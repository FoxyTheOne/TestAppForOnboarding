# Памятка: правила безопасности Firestore

Файл правил: [`firestore.rules`](../firestore.rules) в корне проекта.
Общий разбор Firebase в приложении (что где хранится, сценарии, ответственность) – [FIREBASE.md](FIREBASE.md).
Это **копия** того, что опубликовано в Firebase Console. Меняйте сначала файл, потом вставляйте его
в консоль –
так правила хранятся в git вместе с кодом и не теряются.

---

## 1. Что это и зачем

Ключ Firebase лежит внутри каждого APK, поэтому писать в базу может **кто угодно**, а не только ваше
приложение.
Правила – это охранник на сервере Google: на каждое чтение и запись он отвечает «можно» или
«нельзя».
Код приложения тут ни при чём – правила работают на сервере.

Если правило не пускает, приложение получает ошибку `PERMISSION_DENIED`
(в Logcat: `FirebaseFirestoreException: PERMISSION_DENIED: Missing or insufficient permissions`).

---

## 2. Словарик

| Что написано                                  | Что значит                                                                                             |
|-----------------------------------------------|--------------------------------------------------------------------------------------------------------|
| `rules_version = '2';`                        | Версия **языка** правил, а не ваших правил. Всегда `'2'`, менять не нужно (версии 3 нет)               |
| `match /users/{userId}`                       | «Правила для документов в коллекции `users`». `{userId}` – переменная, туда подставляется id документа |
| `allow read / create / update / delete: if …` | Разрешить действие, если условие истинно. Каждое действие – отдельно                                   |
| `request.auth`                                | Кто стучится. `null` – человек не вошёл в аккаунт                                                      |
| `request.auth.uid`                            | id пользователя в Firebase Auth                                                                        |
| `request.resource.data`                       | Каким документ станет **после** записи (при `set + merge` – целиком, со старыми полями)                |
| `resource.data`                               | Каким документ был **до** записи                                                                       |
| `.diff(resource.data).affectedKeys()`         | Какие поля меняются этой записью                                                                       |
| `.keys().hasOnly([...])`                      | «В документе нет полей, кроме перечисленных»                                                           |
| `x is string`, `x is list`                    | Проверка типа                                                                                          |
| `x.size() <= 100`                             | Длина строки или количество элементов списка                                                           |
| `x.matches('^…$')`                            | Проверка по регулярному выражению (формат)                                                             |
| `&&` / `\|\|`                                 | «и» / «или»                                                                                            |
| `match /{document=**}` + `if false`           | «Всё, что не разрешено выше, – запрещено». Страховка, не удалять                                       |

## 3. Текущие лимиты и где они должны совпадать

Лимит в правилах и в приложении **обязан совпадать**. Если в приложении можно ввести больше, чем
разрешают правила,
пользователь увидит ошибку сохранения.

| Поле в Firestore         | Правило                                              | Где ограничено в приложении                                                                                                      |
|--------------------------|------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------|
| `username`               | строка ≤ 100, буквы + пробел/дефис/апостроф          | `domain/entities/PersonNameRules.kt` → `MAX_LENGTH` и правила символов; к полю ввода подключается через `applyPersonNameRules()` |
| `childName`              | строка ≤ 100                                         | то же самое                                                                                                                      |
| `childGender`            | строка ≤ 20                                          | выбор из вариантов: `BOY` / `GIRL`                                                                                               |
| `childIsItABoy`          | строка ≤ 20                                          | выбор: `YES` / `NO` / пусто                                                                                                      |
| `childHobbies`           | массив ≤ 20 штук (или строка ≤ 2000 – старый формат) | чипы из `res/values/arrays.xml` → `hobbies_array` (сейчас 11)                                                                    |
| `childBirthDate`         | строка `ГГГГ-ММ-ДД` или пусто                        | только через календарь, формат задаёт `toMySaveFormatString()`                                                                   |
| `createdAt`, `updatedAt` | –                                                    | ставит сервер (`FieldValue.serverTimestamp()`)                                                                                   |

Имена полей заданы в `data/dataSource/firebase/UserFirestoreFields.kt`, превращение профиля в
документ –
в `UserFirestoreMapper.kt`.

## 4. ГЛАВНОЕ ПРАВИЛО ПОРЯДКА

> **Сначала публикуем правила, потом выпускаем приложение.**

Правила действуют сразу на все версии приложения у всех пользователей. Если выпустить приложение,
которое пишет новое поле, раньше правил – у всех, кто обновился, сохранение профиля будет
отклоняться.

Правила должны пускать **и старые, и новые версии** приложения одновременно: люди обновляются не в
один день.

## 5. Что менять в правилах при изменениях в программе

### 5.1. Добавили новое поле в профиль

Пример: появилось поле «город» – `childCity`.

В приложении:

1. `UserFirestoreFields.kt` → `const val CHILD_CITY = "childCity"`
2. `UserPresentation`, `OnboardingAnswers`, `OnboardingAnswersDto` (+ маппинг в `StoredModels.kt`)
3. `UserFirestoreMapper.toFirestoreMap()` и `fromDocument()`
4. Лимит длины для поля ввода, если поле вводится вручную (для имён – `PersonNameRules`; для новых
   полей – по тому же образцу)

В `firestore.rules`:

```
function allowedFields() {
  return ['username', 'childGender', 'childIsItABoy', 'childName',
          'childHobbies', 'childBirthDate', 'createdAt', 'updatedAt',
          'childCity'];                                     // ← добавили имя
}

function hasValidValues(data) {
  return ...
    // ← добавили проверку. Поле может отсутствовать в старых документах,
    //   поэтому «нет поля ИЛИ это строка нужной длины»
    && (!('childCity' in data) || (data.childCity is string && data.childCity.size() <= 100));
}
```

> Почему `!('childCity' in data) || …`: у старых пользователей этого поля ещё нет. Если написать
> просто `data.childCity is string`, правило не пустит их документы, пока они не обновят приложение.

### 5.2. Переименовали поле

Пример: `username` → `parentName`.

- Добавьте **новое** имя в `allowedFields()` и в `hasValidValues` (с проверкой «поля может не
  быть»).
- **Старое имя не удаляйте**, пока все пользователи не перешли на новую версию и данные не
  перенесены миграцией (`MigrateUserDataRepository`).
- Проверку старого поля в `hasValidValues` тоже сделайте мягкой: `!('username' in data) || …`

### 5.3. Изменили формат поля

Пример – как было с хобби: строка → массив. Разрешаем **оба** формата через «или»:

```
&& ((data.childHobbies is list && data.childHobbies.size() <= 20)
    || (data.childHobbies is string && data.childHobbies.size() <= 2000))
```

Старый вариант можно убрать, когда во всех документах формат новый.

### 5.4. Изменили лимит длины

Поменяйте число **в двух местах**: в правилах (`size() <= …`) и в приложении (для имён –
`PersonNameRules.MAX_LENGTH`; тест `PersonNameRulesTest` напомнит, если забудете).
Если лимит **увеличиваете** – сначала правила. Если **уменьшаете** – сначала приложение.

### 5.5. Добавили больше хобби

Если вариантов в `hobbies_array` стало больше 20 – увеличьте `data.childHobbies.size() <= 20`.

### 5.6. Новая коллекция

Пример: заметки пользователя `users/{userId}/notes/{noteId}`.
Без нового правила она **закрыта** (страховка в конце файла). Добавьте блок внутри
`match /users/{userId}`:

```
match /notes/{noteId} {
  allow read, delete: if isOwner(userId);
  allow create, update: if isOwner(userId)
    && request.resource.data.keys().hasOnly(['text', 'createdAt'])
    && request.resource.data.text is string
    && request.resource.data.text.size() <= 5000;
}
```

### 5.7. Поле больше не используется

Ничего делать не обязательно: лишнее разрешение не мешает. Можно убрать, когда поле исчезло из всех
документов.

### 5.8. Чего НИКОГДА не делать

- `allow read, write: if true;` – база открыта всему интернету.
- «Тестовый режим» из мастера Firebase (`if request.time < timestamp.date(...)`) – через 30 дней
  база
  перестанет принимать любые записи, приложение «сломается» у всех.
- Удалять последний блок `match /{document=**} { allow read, write: if false; }`.

## 6. Как проверить и опубликовать

1. Firebase Console → проект **exampleappforonboarding** → **Firestore Database** → вкладка *
   *Правила (Rules)**.
2. **Скопируйте текущие правила себе** (на случай отката). История публикаций тоже есть в консоли.
3. Вставьте содержимое `firestore.rules`. Пока не публикуйте.
4. Нажмите **Rules Playground** и проверьте сценарии:

   | Тип | Путь | Авторизация | Данные документа | Ожидание |
               |---|---|---|---|---|
   | get | `users/abc` | вкл., UID `abc` | – | ✅ разрешено |
   | get | `users/abc` | вкл., UID `xyz` | – | ❌ запрещено |
   | get | `users/abc` | выкл. | – | ❌ запрещено |
   | create | `users/abc` | UID `abc` | пример ниже | ✅ разрешено |
   | create | `users/abc` | UID `abc` | пример + `"hack": "x"` | ❌ запрещено |
   | create | `users/abc` | UID `abc` | пример, но `childBirthDate: "19.05.2020"` | ❌ запрещено |

   Пример данных документа:
   ```json
   {
     "username": "Мама",
     "childGender": "BOY",
     "childIsItABoy": "YES",
     "childName": "Ваня",
     "childHobbies": ["chess", "books"],
     "childBirthDate": "2020-05-19"
   }
   ```
5. Если всё совпало – **Опубликовать (Publish)**. Правила начинают действовать примерно через
   минуту.
6. Проверьте в приложении: регистрация, повторное прохождение анкеты (сохранение в Firebase),
   удаление аккаунта.
7. Что-то сломалось → верните старые правила (вставить копию или выбрать прошлую версию в истории) →
   разбирайтесь
   по ошибке `PERMISSION_DENIED` в Logcat.
